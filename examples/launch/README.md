# Wiring a real launch (worked example)

`run_log.jsonl` here is **SYNTHETIC** — generated by
`scripts/gen_launch_example.py`, not captured from production. It exists to show
the wiring end to end so you can replace one file with your own log.

What it demonstrates: a contract decided `AUTO` for one segment, that segment
then drifted, and the recorded baseline caught it.

```
python scripts/check_rollback_baseline.py \
  examples/demo_contract.json examples/launch/run_log.jsonl --window-size 100
```

```
rollback baseline check
  window size: 100 cases   required consecutive breaches: 2
  cases: 600   without an outcome (skipped, not guessed): 3

  routine_faq            AUTO   triggered                observations=400
      baseline=0.9483
      window 1: 98/100 = 0.9800
      window 2: 97/100 = 0.9700
      window 3: 90/100 = 0.9000
      window 4: 92/100 = 0.9200
```

## The four steps

1. **Decide before launch.** `decide` writes one `rollback_triggers` entry per
   `AUTO` segment, with the Wilson lower bound it computed as the baseline. That
   number is frozen at decision time — it cannot be re-fitted after the fact.
2. **Ship only the `AUTO` segments.** The `FENCE`/`HOLD` ones stay with a human.
3. **Log one line per handled case**, in time order:

   ```json
   {"segment": "routine_faq", "ok": true}
   {"segment": "routine_faq", "ok": false}
   ```

   `ok` must be a boolean. A case with no outcome may omit it: it is skipped and
   counted, never treated as a failure or a success.
4. **Check the baseline as the windows close.** `--fail-on-trigger` exits 2 so a
   pipeline can page someone.

## Two different bridges, do not mix them up

| question | tool | input |
|---|---|---|
| What should we ship now? | `import` → `decide` | an **offline eval**, counts per segment |
| Was that decision right? | `check_rollback_baseline.py` | **runtime logs**, one line per case |

`logs_to_counts.py` converts the second into the first, which is the honest way to
re-decide later: last week's live traffic becomes this week's evidence. That is
also the one path where a bad baseline can be caught in the act rather than in
retrospect.

## What the checker refuses to do

- **A partial window never triggers.** 90/95 is not a window; the missing five
  cases are exactly the ones that might have failed.
- **Silence is not success.** `contract_redline` appears in the contract and
  never in the log, and is reported as `not auto; no observations` — not as
  healthy.
- **No baseline for non-`AUTO` segments.** Their log lines are reported, but
  there is no pre-registered claim to compare them against, so no verdict is
  invented.
- **No re-derivation of the baseline.** It is read from `decide`, so the check and
  the ship decision cannot drift apart.

## Limits

- **The log here is fabricated.** It proves the wiring works, not that the
  baseline is well calibrated.
- **Windows are counts, not time.** A success rate needs a denominator; a clock
  does not provide one. If your traffic is bursty, choose the window size from
  your expected daily volume and keep it fixed for the whole launch.
- **A trigger means the assumption broke, not that harm occurred.** It says the
  observed rate fell below what the offline evidence promised — worth acting on,
  but not by itself an incident report.
- **Coverage is not checked against reality.** If production segments do not
  match the contract's segment names, everything shows up as
  `unknown_segments` and no baseline fires. That failure is loud on purpose.
